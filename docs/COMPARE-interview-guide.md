## 一、先讲清楚对方那个仓库是什么

| 项 | 值 |
|---|---|
| 仓库 | `Snailclimb/interview-guide` |
| Star / Fork | **3543 / 802** |
| 语言 | Java（Java 25，用虚拟线程） |
| 许可 | AGPL-3.0（强传染：二次分发必须开源） |
| 最近推送 | 2026-10 |
| 一句话 | 一个功能完整的**AI 面试平台**：简历分析 + 文字/语音面试 + 面试日程 + 知识库 RAG + 题库 |

### 1.1 它的技术栈（为什么"看起来是个平台"）

```
Spring Boot 4.1 + Java 25（虚拟线程）
Spring AI 2.0 + Spring AI Agent Utils（Skill 资源加载）
PostgreSQL 16 + pgvector（关系库 + 向量库）
Redis 6 + Redisson（缓存 + Stream 消息队列）
Apache Tika 2.9（文档解析）  iText 8（PDF 导出）  MapStruct（对象映射）
React 18 + TypeScript 5.6 + Vite
RustFS / MinIO（S3 兼容对象存储）
Flyway（数据库版本迁移）
Docker Compose（一键起前端+后端+PG+Redis+存储）
```

**这个组合本身就是"企业级后端"的标准答案**：关系库 + 缓存/队列 + 对象存储 + 向量库 + 前端构建链 + 容器编排。

### 1.2 它的六个业务模块

| 模块 | 核心机制（README 明确写了） |
|---|---|
| **简历** | PDF/DOCX/DOC/TXT 解析；Redis Stream **异步**分析，带处理进度状态（待分析/分析中/完成/失败）；失败自动重试≤3 次；**内容哈希去重**；分析报告导出 PDF |
| **模拟面试** | `SKILL.md` 定义 10+ 方向（Java 后端、阿里/字节/腾讯专项、前端、算法、系统设计、测开、AI Agent…）；**历史题目去重**；总时长滑块→各阶段按比例分配；多轮智能追问；**文字/语音共用同一评估引擎**（分批评估+结构化输出+二次汇总+降级兜底）；报告导出 PDF |
| **面试安排** | 规则+AI 双引擎解析飞书/腾讯/Zoom 邀请；日/周/月日历拖拽；定时任务自动过期；可配提醒 |
| **语音面试** | WebSocket + 千问3 语音（ASR/TTS/LLM 一套 Key）；句子级并发 TTS，首包 200ms；**服务端 VAD** 自动断句+实时字幕；回声防护；暂停/恢复；Micrometer 埋点 |
| **知识库** | 文档上传→分块→**异步向量化**（pgvector）；查询改写+相似度阈值+TopK；**SSE 流式**打字机效果；分类/下载/重向量化/统计 |
| **题库与专项面试** | 从已向量化文档生成主问题+参考答案+关键点+评分标准+追问；Redis Stream 异步生成；严格容量校验（追问数是硬约束，不够就禁用选项+后端兜底）；交卷后异步评估+趋势统计+PDF |

### 1.3 它的工程细节（这些才是 star 高的原因）

- `@RateLimit` 可重复注解 + AOP + **Redis Lua** 原子限流
- Redis Stream 生产者/消费者模板（异步任务统一封装）
- 统一响应 `Result<T>` + 全局异常处理
- Flyway 管 schema，启动自动迁移
- Prompt 模板集中放 `resources/prompts/`（StringTemplate）
- Prompt 安全（`common/ai/`）
- 配置写用户目录 `~/.interview-guide/`，API Key 加密落盘
- 完整 Compose + dev Compose 分离（开发只需 PG/Redis/存储三个容器）

### 1.4 它自己承认的短板（README 的"已知问题"）

```
语音：端到端延迟偏高（服务端音频中转）、无耳机时回声泄漏、TTS 音色单一、弱网断续
```
其余模块它没有写局限——**评估是否可信、判定是否稳定、答案有没有依据，README 里没有对应机制**。

### 1.5 它的商业模式（影响你怎么用它）

完整功能免费开源（AGPL-3.0），但**配套教程是付费的**。
这意味着：代码可以学，但要"讲清楚为什么这么做"得买课。

## 二、我们这个项目是什么

| 项 | 值 |
|---|---|
| 形态 | 单进程 Python，**零第三方运行时依赖**（只用标准库） |
| 规模 | 业务 9,612 行 / 39 个文件；测试 3,313 行 / 27 个文件 / **322 条用例** |
| 门禁 | **9 关**（单测、评估回归、知识库、题库、不变量、审计重放、校准、部署、Docker 路径） |
| 题库 | 722 题 / 46 话题 |
| 许可 | 自用项目，未选许可 |

### 2.1 一轮面试的数据流（九个动作）

```
① 鉴权（签名 cookie → 用户）
② evaluator：五维打分 + 判定（证据必须原文可查）
③ memory：抽事实 + 矛盾检测（旧值 vs 新值）
④ probe_tree：要素覆盖/回避/未答出（每要素最多 2 次）
⑤ state_machine：总时长 → 阶段预算 → 阶段题量 → 木梯层级
⑥ interviewer：生成下一问（LLM）
⑦ ledger：每一笔入账（append-only，fold 幂等，可验链）
⑧ invariants：8 条运行时不变量，fatal → 输出不采纳
⑨ persist：SQLite 快照（含断点续答）
```

### 2.2 我们真正在解决的问题（对方 README 没提的）

| 机制 | 解决什么 | 证据 |
|---|---|---|
| **判定权在阈值不在模型** | 模型说 pass 但分数不够 → 以阈值为准，冲突留痕 `verdict_conflict` | `normalize_eval` + INV-05 |
| **校准** | 阈值不是拍脑袋 | 57 条标注，5 折 CV 80%，bootstrap CI **[70%, 91%]** |
| **可复现** | 同样输入是否同样输出 | cassette 重放，快照逐字段比对 |
| **自检** | 跑歪了能不能自己发现 | 8 条不变量，fatal 计数进报告 |
| **预算与降级** | 模型慢/贵/挂 | 三级降级 + 每轮 token/成本/延迟入账 |
| **结构化上下文** | 长会话忘了前面 | 阶段简报（聚合，**不新增模型调用**） |

### 2.3 我们缺什么（现场核对，不猜）

| 能力 | 对方 | 我们 | 结论 |
|---|---|---|---|
| 简历多格式解析 | Tika（PDF/DOCX/DOC/TXT） | `documents.py`：PDF 三路回退 + DOCX | 大致相当，我们没 DOC/TXT 全覆盖 |
| 异步任务队列 | Redis Stream + 重试 + 去重 | 无（同步） | **缺** |
| 向量检索 RAG | pgvector + 查询改写 + TopK | 无真实向量检索 | **缺** |
| 语音面试 | WebSocket + ASR/TTS + VAD | 无 | **缺（最大差距）** |
| Scheduler/日历 | 有 | 无 | **缺** |
| PDF 导出 | iText | 只有 JSON/HTML 报告 | **缺**（小工作量） |
| 限流 | 注解 + Redis Lua | 无（`auth.py` 明写"不做"） | **缺** |
| 多 Provider 管理界面 | 设置页切换 + 加密落盘 | 环境变量/命令行 | 简化版 |
| 题库生成闭环 | 文档→向量→出题→容量校验 | 722 题静态库 + AI 复审 | 各有偏重 |
| 部署 | Compose 全家桶 | Compose 单服务 + WSL 路径 | 对方更完整 |
| 评估可解释性 | 未提 | 账本+不变量+校准+CI | **我们更强** |

## 三、本质区别（一句话）

> **他们在做一个面向用户的面试产品；我们在做一个能被追问"凭什么"的判定系统。**
>
> 他们的难点在"集成与规模"（多组件、异步、流式、多人用）；
> 我们的难点在"可信与可复现"（判定权归属、证据可查、结果稳定、阈值有据）。

**所以不要用"功能条数"对比**：他们功能多；我们证明链完整。面试官问"你这个能直接用吗"，答案是"能跑，但更值得看的是它怎么保证判定不飘"。

## 四、该抄什么、不该抄什么

按我们已有 `docs/why-not-copy.md` 的四道闸（是否解决真问题 / 成本是否可控 / 是否会破坏现有保证 / 能否验证）：

| 对方机制 | 抄吗 | 理由 |
|---|---|---|
| SKILL.md 驱动出题方向 | **抄**（低成本） | 我们的方向配置在 `config.PHASE_CONFIG`/role 上，扩成文件更易维护 |
| 历史题目去重 | **抄** | 我们有 probe_tree 但只防"同一要素重复"，没防"同一题重复" |
| 时长→阶段题量 | 已抄（并加了 parity 保护） | 我们踩过坑：权重手写导致评估退化 |
| 统一评估引擎（文字/语音共用） | 暂不抄 | 我们没有语音，没有第二个输入源 |
| Redis Stream 异步 | 暂不抄 | 单机同步够用；引入要带监控与失败重放，成本高 |
| pgvector RAG | 有条件抄 | 真需要"按我的项目文档出题"才值得 |
| 限流注解 | 抄（简化版） | 登录接口需要，用内存令牌桶即可 |
| PDF 导出 | **抄**（优先） | 面试报告给面试官看，PDF 比 JSON 有用 |
| Flyway 式迁移 | 已部分有（ALTER 迁移） | 我们 `persist.py` 已做旧库迁移 |

| # | 事项 | 为什么 | 工作量 |
|---|---|---|---|

### 不建议做

- 自建日历/日程（和"面试判定"无关，只为凑功能）
- 多 Provider 图形化管理（环境变量够用）
- 换 Java/Spring 重写（我们的价值在保证机制，不在技术栈）

## 六、如果只记三句

1. **对方 3543★ 靠的是"企业级集成 + 完整业务闭环"**，六个模块、异步/流式/向量/语音全上。
2. **我们靠的是"判定可审计 + 可复现 + 有校准"**，规模小但每条结论有证据。
3. **差距集中在"输入侧的丰富度"（语音、RAG、异步）**；
   **优势集中在"输出侧的可信度"（账本、不变量、阈值权威、CI）**。
