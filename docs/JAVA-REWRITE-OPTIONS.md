# 要不要改成 Java + Spring Boot + Spring AI：算一次账

结论先放前面：**"只需要把 API 改了"这个判断只覆盖了我们代码的 6.6%。**
真正的工作量在另外 93% —— 而那部分恰好是我们这个项目唯一值钱的东西。

---

## 一、先把账算清楚（现场统计）

```
业务代码        9,612 行 / 39 个文件
测试代码        3,313 行 / 27 个文件 / 322 条用例
其中：
  webui.py      777 行（8.1%）  ← HTTP 层，Java 里对应 Controller
  llm.py        633 行（6.6%）  ← 调模型层，Java 里对应 Spring AI
  其余 36 个文件 8,202 行（85.3%）← 状态机/账本/不变量/评估/校准/持久化/报告…
```

**"改 API"改的是 633 行里的那 100 多行真正发请求的部分。**
剩下 85% 是：`state_machine`（298 行）、`probe_tree`、`evaluator`（247）、`ledger`（259）、
`invariants`、`memory`（269）、`budget`、`persist`（244）、`briefing`、`store`、`session`（549）、`config`（465）……

### Java 化之后代码量会变多，不会变少

| 项 | Python | Java 估算 | 说明 |
|---|---|---|---|
| 业务逻辑 | 9,612 | **15,000–19,000** | Java 更啰嗦（类型、getter、DTO、异常声明） |
| 测试 | 3,313（322 用例） | **5,000+**（JUnit 5） | 断言写法更长，还要 mock 框架 |
| 门禁 | 9 关（`check.py`） | 全部重写 | 评估回归、校准、审计重放都得重新接 |
| 校准基线 | 已跑出 80% / CI[70,91] | **必须重跑** | 换了实现，阈值和一致性都要重新证明 |

**工作量估算（一个人）**：3–5 周做出"能跑"，再 1–2 周补回门禁与校准。
而且这期间原来的 322 条用例、9 道门禁全部失效，等于**把已有的质量保障清零重来**。

---

## 二、为什么"只改 API"这个想法会不成立

因为 API 调用是**最不成问题的一层**。真正难的是我们花了几轮才做出来的东西：

| 我们的机制 | 和"调模型"有关吗 | 换语言要重做吗 |
|---|---|---|
| 判定权在阈值（模型说 pass 但分数不够 → 以阈值为准） | 无关 | 要重做 |
| 8 条运行时不变量（fatal 不采纳输出） | 无关 | 要重做 |
| append-only 账本 + `fold()` 幂等 + 验链 | 无关 | 要重做 |
| cassette 重放（同输入逐字段比对） | 无关 | 要重做 |
| 57 条标注 + 5 折 CV + bootstrap CI | 无关 | 要重跑 |
| 阶段预算分配 + parity 保护 | 无关 | 要重做 |
| 探针树（要素覆盖/回避/最多问 2 次） | 无关 | 要重做 |

**这七件事没有一件是"改 API"能顺带完成的。**

## 三、四条路，各自代价与收益

### 方案 A：全量重写（Java 25 + Spring Boot 4.1 + Spring AI 2.0）

| 项 | 内容 |
|---|---|
| 工作量 | 4–7 周（一个人，含门禁与校准重建） |
| 收益 | 会用 Spring 全家桶；多用户并发能力强；简历上"Java 后端 + Spring AI"叙事完整 |
| 代价 | 3–5 周内没有新功能；质量保障清零重来；放弃"零依赖、拿到就跑"的优势 |
| 风险 | 环境门槛：本机是 **JDK 21**，项目要 **JDK 25**；还要 Gradle、Node/pnpm |

### 方案 B：只抽象"模型层"，语言不变（推荐先做这个）

把 `llm.py` 里散落的调用整理成一个"类 Spring AI"的客户端抽象：

```
ChatClient
 ├─ .prompt().system(...).user(...).call().content()      ← 普通文本
 ├─ .call().entity(Schema)                                 ← 结构化输出（复用它已有的 JSON 重试）
 ├─ advisors = [Memory, Guard, Logger]                     ← 拦截链
 └─ .stream()                                              ← 预留流式
```

| 项 | 内容 |
|---|---|
| 工作量 | 1–2 天 |
| 收益 | 代码结构立刻"像框架"；面试能讲清 Advisor/Memory/结构化输出是什么；现有 322 用例全绿 |
| 代价 | 不是真的 Spring AI，讲的时候必须说清"我是自己实现的同构抽象" |

### 方案 C：Java 网关 + Python 核心（旁路）

Spring Boot 提供 REST 与 Spring AI 调用，把 Python 当内部服务。

| 项 | 内容 |
|---|---|
| 工作量 | 3–5 天做出 demo 质量 |
| 收益 | 简历上真的有 Spring Boot 服务 |
| 代价 | 两套运行时、两个部署单元、调试链路变长；**对我们的判定机制毫无帮助** |

### 方案 D：不改，把精力放 P0 功能

PDF 报告、登录限流、题目去重、CSRF —— 每项半天，直接提升"能不能用"。

## 四、如果真要做 A，正确的迁移顺序（不要一把梭）

用"绞杀者模式"（strangler）：

```
第 1 步  用 Python 现有实现做"金标准"：把 20 场面试的输入/输出存成 cassette
第 2 步  搭 Java 骨架：Spring Boot + Spring AI + 一个 /api/health
第 3 步  先移植"最独立"的模块：documents（解析）、store（报告渲染）
第 4 步  移植 evaluator，跑"同输入对比"：Java 输出 vs Python 记录，逐字段比对
         —— 不一致率高就停下，先修差异，别继续往下搬
第 5 步  移植 state_machine / probe_tree / ledger / invariants（这层最难，最后做）
第 6 步  重跑校准（57 标注）与 9 道门禁，拿到新的 CV / CI
第 7 步  切流：Java 服务对外，Python 退役（但保留 cassette 以备回滚）
```

**关键检查点在第 4 步**：如果 Java 版评估结果和 Python 版对不上，说明"行为等价"没做到，此时继续搬就是灾难。

## 五、一个便宜的替代方案：证明你会 Spring，不必重写主项目

如果你想的是"面试时能讲 Spring AI"，成本最低的做法是**另建一个 200–300 行的小服务**：

```
spring-ai-demo/
├── pom.xml / build.gradle
├── DemoApplication.java
├── ChatController.java          // GET /api/ask?q=...  → chatClient.prompt().user(q).call().content()
└── StructuredController.java    // POST /api/eval     → .entity(EvalResult.class) 结构化输出
```

跑起来、截图、把代码放进作品集。**30 分钟能做完，能讲清 ChatClient / Advisor / 结构化输出三件事**，
而且完全不碰主项目的 322 条用例和 9 道门禁。

## 六、法律与卫生提醒

| 事项 | 说明 |
|---|---|
| **不要复制他的代码** | interview-guide 是 **AGPL-3.0**：复制进你的项目，你的项目也要按 AGPL 开源 |
| 可以学的是"设计" | Skill 目录结构、两阶段限流、分批评估+二次汇总、fencing —— 这些是通用工程思想，重写实现没问题 |
| 依赖许可 | Spring Boot / Spring AI 是 Apache-2.0，商用友好 |

## 七、我的建议（按你的目标选）

| 你的目标 | 建议 |
|---|---|
| 想让项目"更像平台"、能多用户 | 方案 A 的一部分：**只做方案 C 的网关**不够，得真迁移；建议先把 P0 做完再动 |
| 想面试时能讲 Java/Spring AI | **方案 B + 第五节的 demo 服务**，两天内完成，风险最低 |
| 想学 Spring 全家桶 | 直接 clone interview-guide 跑起来读，比拿自己的项目练手更高效 |
| 想让项目更好用 | **方案 D**，每项半天，收益最直接 |

**一句话**：改语言不等于改 API。我们 93.4% 的代码和"调模型"无关，而那部分正是这个项目存在的理由。
